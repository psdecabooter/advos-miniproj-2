\section{Introduction}

The UNIX pipe is the oldest IPC mechanism still in daily use, and its cost
model is usually taken on faith. The buffer is sixteen pages, writers block
when it fills, and larger writes amortize better. We measured those claims and
then asked where the time goes. The dominant variable turns out to be
placement and not payload size.

\section{Apparatus and method}
\label{sec:apparatus}

We ran everything on an Ubuntu 24.04 guest with a custom Linux 7.2.4 kernel on
arm64, eight vCPUs and \SI{12}{GiB} of RAM, under QEMU with \texttt{hvf} on an
Apple M1. The page size is \SI{4}{KiB} and \texttt{pipe-max-size} is
\SI{1}{MiB}, so the resize sweep runs unprivileged. Absolute figures include
hypervisor overhead, but the placement comparisons do not depend on it.

We place the processes with \texttt{sched\_setaffinity} after the
\texttt{fork}, since \texttt{taskset} cannot express parent on core 0 and child
on core 1.
Each configuration runs five times and we take the minimum, since noise can
only add time. Throughput is a rate, so we report the maximum and never a
mean.

\section{Choosing a clock}

\textbf{Variables.} The cause is the clock API. The effects are accuracy and
granularity. \textbf{Hypothesis.} \texttt{clock\_gettime} can resolve a single
exchange and \texttt{gettimeofday} cannot.

We compared \texttt{clock\_gettime(CLOCK\_MONOTONIC)}, \texttt{gettimeofday},
and \texttt{cntvct\_el0}, which is this architecture's analogue of
\texttt{rdtsc}. Timing \texttt{sleep(5)}, all three recovered \SI{5.0024}{s}
and agreed within \SI{53}{ppm}, so all three are accurate. We then read each
clock $10^6$ times back to back. The quantum is \SI{\nCgtQuantum}{ns} for
\texttt{clock\_gettime}, \SI{\nCcPeriod}{ns} for \texttt{cntvct\_el0}, and
\SI{1}{\micro\second} for \texttt{gettimeofday}, and
\SI{\nGtodZero}{\percent} of adjacent \texttt{gettimeofday} readings are
identical. A clock that cannot separate two of its own calls cannot measure a
\SI{\nLatSameSmall}{ns} exchange, so we discarded it. We chose
\texttt{clock\_gettime}, because it shares the quantum of the raw counter and
is portable. Neither cycle counter caveat bites here, since the clock is frequency
invariant and reads within \SI{\nSkewMax}{ns} across cores.

\section{Latency}

\textbf{Variables.} The causes are payload size and placement. The effect is
one-way latency, taken as half a round trip so that only one clock is
involved. \textbf{Hypothesis.} Flat while the fixed cost dominates, then linear
once the copying dominates.

Figure~\ref{fig:latency} shows that shape. Below \SI{4}{KiB} every curve is
flat, so the cost is per exchange and not per byte. Above \SI{16}{KiB} the
growth is linear. The part we did not expect is the constant offset in the flat
region. Same-core costs \SI{\nLatSameSmall}{ns} and cross-core
costs \SI{\nLatCrossSmall}{ns}, a penalty of \SI{\nLatPenalty}{ns} that does
not depend on the payload. Unpinned runs track the cross-core curve, so the
scheduler spreads the pair by default.

\section{Throughput}

\textbf{Variables.} The causes are chunk size and placement. The effect is
sustained one-way bandwidth, acknowledged once for the whole transfer.
\textbf{Hypothesis.} Throughput rises as the fixed per-write cost amortizes,
then falls once the chunks exceed the capacity.

Figure~\ref{fig:thr} shows that the first half is right and the second half is
wrong. Only the cross-core curve collapses, from \SI{\nThrCrossPeak}{MiB/s} at
\SI{8}{KiB} to \SI{\nThrCrossBig}{MiB/s} at \SI{512}{KiB}. The same-core curve
climbs to \SI{\nThrSamePeak}{MiB/s} and stays flat through chunks eight times
the capacity. This rules out blocking as the explanation, because the pipe is
the same size in both cases, so the same-core writer blocks just as often.
What is lost is overlap, and Section~\ref{sec:time} accounts for it.

\section{Where the time goes}
\label{sec:time}

\textbf{Variables.} The causes are placement and the ratio of payload to
capacity. The effects are the split of elapsed time between user, kernel and
blocked, and the context switches per exchange. \textbf{Hypothesis.} If the
cross-core penalty is a scheduling cost, both placements should issue the same
system calls and the same context switches, and the difference should appear as
time that is neither user nor kernel.

A nonblocking pipe accepts exactly \SI{65536}{bytes} before \texttt{EAGAIN},
which matches \texttt{F\_GETPIPE\_SZ} and the sixteen page folklore.
Table~\ref{tab:time} accounts for the wall clock with \texttt{getrusage}. At
\SI{4}{B} the same-core pair spends almost all its time in the kernel and none
of it blocked. The cross-core pair does the same work, and \texttt{strace}
confirms two \texttt{write} and two \texttt{read} calls per round trip, but it
is ten times slower, and \SI{\nCrossBlocked}{\percent} of its wall clock is
neither user nor system time. That residue is the \SI{\nLatPenalty}{ns}
penalty, because it is time spent descheduled while waiting for a wakeup on
another core.

The context switch column connects this to the capacity. There are
$\nCtxSmall$ voluntary switches per round trip at \SI{4}{B} and $\nCtxBig$ at
\SI{512}{KiB}, which is exactly $2\lceil \text{size}/\text{capacity}\rceil$
against the measured \SI{64}{KiB}. Figure~\ref{fig:resize} then makes the
capacity the independent variable, and the knee follows the configured size, so
the correlation is causal.

\section{Conclusions}

Pipe cost is set by two quantities, and the payload size is only one of them.
The capacity fixes how many handoffs a transfer needs, and the placement fixes
the price of each one. So spreading a pair across cores only helps while the
messages stay below the capacity, and past that point the pair is four times
faster on a single core. Everything ran virtualized, so the absolute latencies
carry hypervisor overhead, and no PMU was available in the guest, so
Table~\ref{tab:time} rests on \texttt{getrusage} and \texttt{strace}.
