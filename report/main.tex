\section{Introduction}

The cost model of a UNIX pipe is usually assumed and not measured.
The buffer is said to be sixteen pages, writers block when it fills, and
larger writes amortize better. We measured those claims and asked where the
time goes. Placement matters more than payload size. Everything ran in a QEMU guest, so the
absolute numbers carry hypervisor overhead, and we rely on the comparisons
between placements.

\section{Apparatus and method}
\label{sec:apparatus}

We ran everything on an Ubuntu 24.04 guest with a custom Linux 7.2.4 kernel on
arm64, eight vCPUs and \SI{12}{GB} of RAM, under QEMU with \texttt{hvf} on an
Apple M1. The page size is \SI{4}{KiB} and \texttt{pipe-max-size} is
\SI{1}{MiB}, so the resize sweep runs unprivileged.

We pin the processes with \texttt{sched\_setaffinity} after the
\texttt{fork}, since \texttt{taskset} cannot place the two separately. Each
configuration runs five times. Noise can only add time, so we report the
minimum latency and the maximum throughput, because throughput is a rate.

\section{Choosing a clock}

\textbf{Variables.} The cause is the clock API. The effects are accuracy and
granularity. \textbf{Hypothesis.} \texttt{clock\_gettime} can resolve a single
exchange and \texttt{gettimeofday} cannot.

We compared \texttt{clock\_gettime}, \texttt{gettimeofday} and
\texttt{cntvct\_el0}, which is this architecture's version of
\texttt{rdtsc}. We timed \texttt{sleep(5)}, and all three recovered
\SI{\nSleepMean}{s} and agreed within \SI{\nSleepSpread}{ppm}, so all three
are accurate. The shared \SI{\nSleepOver}{ppm} excess over five seconds is
\texttt{sleep} overshooting and not clock error. We then read each
clock $10^6$ times back to back. Figure~\ref{fig:clock} shows the result. Call
cost does not disqualify any of the three. The quantum disqualifies
\texttt{gettimeofday}. \SI{\nGtodZero}{\percent} of its adjacent readings are
identical, so it cannot separate two of its own calls or measure a
\SI{\nLatSameSmall}{ns} exchange. We chose
\texttt{clock\_gettime}, because it shares the quantum of the raw counter and
is portable. Neither caveat for cycle counters applies here. The counter is
frequency invariant, and it reads within \SI{\nSkewMax}{ns} across cores.

\section{Latency}

\textbf{Variables.} The causes are payload size and placement. The effect is
one-way latency, taken as half a round trip so that only one clock is
involved. \textbf{Hypothesis.} Flat while the fixed cost dominates, then linear
once the copying dominates.

Figure~\ref{fig:latency} and Table~\ref{tab:data} show that shape. The flat
region means the cost is per exchange and not per byte. We did not expect the
constant offset in that region. The penalty for crossing cores is \SI{\nLatPenalty}{ns} and it does
not depend on the payload. Unpinned runs track the cross-core curve up to
\SI{256}{KiB}, so the scheduler spreads the pair by default. Above that they
are worse than either pinning, and we do not know why.

\section{Throughput}

\textbf{Variables.} The causes are chunk size and placement. The effect is
sustained one-way bandwidth, acknowledged once for the whole transfer. Each
run streams up to \SI{64}{MiB}, so the acknowledgement is a negligible part of
it. \textbf{Hypothesis.} Throughput rises as the fixed per-write cost amortizes,
then falls once the chunks exceed the capacity.

Figure~\ref{fig:thr} shows the rise, but only the cross-core curve falls.
The same-core curve stays flat through chunks eight times the capacity. Blocking cannot be the explanation, since the pipe is the same
size in both cases and the same-core writer blocks just as often. The
cross-core case loses overlap, because past the capacity the writer stalls
mid-chunk.

\section{Where the time goes}
\label{sec:time}

\textbf{Variables.} The causes are placement and the ratio of payload to
capacity. The effects are the user, kernel and blocked split of elapsed time
and the context switches per exchange. \textbf{Hypothesis.} If the cross-core
penalty is a scheduling cost, both placements issue the same calls and the same
switches, and the difference appears as time that is neither user nor kernel.

A nonblocking pipe accepts exactly \SI{65536}{bytes} before \texttt{EAGAIN},
which matches \texttt{F\_GETPIPE\_SZ} and the sixteen pages we assumed above.
At \SI{4}{B} both placements do the same work, and \texttt{strace} confirms two
\texttt{write} and two \texttt{read} calls per round trip, but the cross-core
pair is ten times slower and most of its wall clock is neither user nor system
time. That residue is time spent descheduled while waiting for a wakeup on another
core, and it is why the cross-core pair is slower.

The context switch column depends on the capacity. The counts match
$2\lceil \text{size}/\text{capacity}\rceil$ against the measured
\SI{64}{KiB}. Figure~\ref{fig:resize} then makes the
capacity the independent variable, and the knee follows the configured size,
so we think the capacity is the cause and not just a correlation.



\section{Conclusions}

Payload size is only one of the two quantities that set pipe cost. The capacity
decides how many handoffs a transfer needs. The placement decides what each
handoff costs. Spreading a pair across cores never helps latency, and it
helps throughput only at small payloads. Everything ran on one machine, so it
is hard to tell whether these numbers hold on other hardware. No \texttt{perf} build
matches this kernel, so Table~\ref{tab:time} rests on \texttt{getrusage} and
\texttt{strace}.
