\section{Introduction}
Inter-process communication (IPC) is a critical trade-off of virtual memory systems.
Before we had virtual memory, IPC was as simple as passing the pointer to the data between the two processes. 
However, when each process is sand-boxed in its own virtual memory environment, the process sending
the data has no way to reason about the addresses receiving process and 
vice-versa. Unfortunately for IPC, virtual memory has countless benefits and is here
to stay.

Enter \pipes, the first and oldest method of IPC chosen by the Linux kernel. 
Linux \pipes create one-way channels between two processes. They contain two file descriptors,
one to write to, and one to read from. In between writes and reads, the transfer payload 
is stored in a kernel-space buffer.

In this report we will:
\begin{enumerate}[label=(\arabic*), nosep]
  \item Evaluate the precision of two Linux timers that will be used for measurement.
  \item Measure the minimum latency of \pipes when sending various payload sizes.
  \item Measure the average throughput of \pipes when continuously sending large payloads. 
\end{enumerate}

\section{Linux Timers}
We tested two types of timers for our experiments. 
The first timer, provided by the header \texttt{time.h}, is \cgt.
We chose \texttt{CLOCK\_MONOTONIC} as the clock to use for \cgt due 
to it having guaranteed monotonicity and being system-wide. 
\cgt provides nanosecond precision.
The second timer, provided by the header \texttt{sys/time.h}, is \gtod.
\gtod finds the time by measuring the clock cycles since the last kernel epoch.
\gtod provides microsecond precision.
\gtod is a much older clock. By the time cpu-cycles were able to measure nanoseconds,
\gtod's interface was already locked-in to microseconds. \cgt was introduced as an api to replace \gtod.
In order to have similar units, we scaled \gtod up to nanoseconds instead of scaling \cgt
down to microseconds. 
We chose to do it this way since it would take advantage of \cgt's
increased accuracy and give us more intuitive numbers for figures.

\section{Linux Pipes}
When data moves between processes in a \pipe, it is not as simple as the other process reading it out of virtual memory.
First, the data must be sent by the \texttt{write} system call. \texttt{write} context-switches into kernel mode and
copies the data into a kernel-space buffer.
Next, the reader must call the \texttt{read} system call. \texttt{read} once again context-switches into kernel mode,
then copies the data in the kernel-space buffer back into a buffer in the user-space of that process.
Often times the reader will be programmed to send back an acknowledgement byte to the writer so it knows the message has
been received. Since \pipes are one-directional, this acknowledgement must be done on a separate \pipe.

We did not test \pipes with any flags enabled or changes to buffer sizes. This means that the kernel is using
the default \pipe buffer size of 64KiB. This also means that \texttt{write} and \texttt{read} operate in blocking mode.
Therefore, \texttt{write} will block until all bytes of the payload are written and \texttt{read} will block
until it reads data from the \pipe.

\section{Evaluation}

\subsection*{Clock Precision}
To evaluate the accuracy of the two timers, we measured against
\texttt{sleep} from the header \texttt{unistd.h} and determined 
the smallest measurable time for the least precise of the two timers.

To measure against \texttt{sleep}, we started the timer, called \texttt{sleep(5)}, then 
measured the final time to get the difference. We did this five times in a loop for each timer,
and took the minimum result. We decided to choose the minimum because we wanted to measure
the limits of the timer rather than measure how fast our context-switching may or may-not be.
Both timers were able to measure to an accuracy of 5.0001 seconds.

To measure the smallest measurable time, we first had to compromise to
instead find the smallest measurable time for \gtod. 
This is because \gtod measures in microseconds instead of 
nanoseconds. To make a one microsecond delay, we summed the numbers from 0 to 99 in a loop. 
We did this this 10 times and took the minimum result. 
Although \gtod measured 1 microsecond, \cgt was able to measure 1308 nanoseconds (1.308 microsecond).
It is important to note that \cgt can measure even smaller timeframes, we just left our work here
since we believe it exemplifies the precision gap between the two timers.

\subsection*{Pipe Latency}
We tested \pipe latency under 10 different payload sizes: 4, 16, 64, 256, 1K, 4K, 16K, 64K, 256K, and 512K bytes. 
Since synchronizing clocks between processes is unwieldy, we measured the time from payload send to acknowledgement acquisition. 
To construct our experiment, we had two processes. The parent process forked itself at the start of execution.  
The parent then sends each payload size 10 times and to account for the acknowledgement latency we half the final time.
At process start, the child enters a loop where it waits for the parent to send data then acknowledges the request.
Both experiments use both \cgt and \gtod timers. 

As seen in Figure~\ref{fig:pipe_latency}, until the payload size reaches ~16KiB, the latency 
appears to be constant. At payload sizes above 64KiB, the latency begins to grow linearly. We suspect 
that this scaling is due to these larger payload sizes hitting the default \pipe buffer size. 
Once the kernel's \pipe buffer is full, the \texttt{write} system call must block until it is emptied enough
for more data to flow.
To further dig into this hypothesis, we used the \texttt{strace} utility to measure the time spent in \texttt{wait4} by the parent process. 
First we tested together the payload sizes below 64KiB, then we tested together the payload sizes above 64KiB.
Using the small payload sizes, \texttt{wait4} took only 15\% of execution time. 
Using the large payload sizes, \texttt{wait4} took 35\% of execution time.
This backs up our hypothesis that smaller payload sizes spend less time waiting. 
However, given more time, testing different kernel buffer sizes would be able to further elucidate
the latency relationship between kernel buffer sizes and payload sizes.

\subsection*{Pipe Throughput}
To measure \pipe throughput, we had a similar parent-child experiment set-up
as we did to test \pipe latency. 
To have a long enough test to get an accurate measure, we sent 64MiB over the \pipe
100 times in a row before receiving the acknowledgement from the child.
This time, since the volume of work is so high, we did not have to account for 
acknowledgement latency.
To calculate the final MiB/s of the \pipes, we performed the test 10 times on each timer,
took the geometric means of the times and then normalized it by the payload size.
Using \cgt, we measured a throughput of 761 MiB/s.
Using \gtod, we measured a throughput of 817 MiB/s.

\section{Conclusion}
Inter-process Communication (IPC) presents many problems and \pipes are just one way to solve them.
Despite their old age, \pipes can still be seen in systems today. Because they are so common,
it is important that we understand their performance properties.
We hope that readers will keep in mind the inherent latency that comes with \pipes and understand
the throughput cost from IPC. 
We also hope the reader measures their payloads and considers changing the kernel \pipe buffer size
if they are consistently sending payloads above 64 KiB.
